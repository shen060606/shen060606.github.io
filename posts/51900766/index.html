Redis 缓存穿透、击穿、雪崩：Go 实战与 singleflight 源码解析

发表于2026-11-09|更新于2026-11-09
|总字数:3.5k|阅读时长:12分钟|浏览量:

穿透、击穿、雪崩，是每一个用 Redis 的人迟早要撞上的三道坎。
本文重点讲前两个的 Go 实现——布隆过滤器挡穿透、singleflight 挡击穿，并逐行拆解 singleflight 的 Do 内部实现。雪崩只列方法。

一、先分清三个名词

这三个词极易混淆，但根因和解法完全不同：

名字 现象 根因 解法
缓存穿透 查一个根本不存在的数据，缓存永远不命中，每次都打库 请求的 key 在 DB 里也没有 空值缓存、布隆过滤器
缓存击穿 一个热点 key 恰好过期的瞬间，海量并发同时打库 同一个 key 的并发请求没被合并 互斥锁、singleflight
缓存雪崩 大批 key 同时过期，或 Redis 整个挂了 TTL 集中 + 没有降级 TTL 加随机、多级缓存、限流降级

一句话概括它们的区别：

  • 穿透是「查的东西根本不存在」，打库的是无效请求。
  • 击穿是「热点 key 刚到期」，打库的是同一份数据的重复请求。
  • 雪崩是「一大批 key 同时死」，打库的是海量正常请求。

下面重点展开前两个。

二、缓存穿透与布隆过滤器

2.1 穿透是怎么发生的

攻击者（或正常业务）不断请求一个数据库中不存在的 id，比如：

请求到达后：

于是每一次这样的请求都会穿透缓存、打到数据库。恶意刷一大波不存在的 id，就能把 MySQL 压垮。

2.2 两个解法

解法一：空值缓存。 查到不存在时，往 Redis 里存一个短 TTL 的空标记（比如 "" 或一个特殊值），下次来就能挡住。缺点是每个不存在的 key 都要占一份内存，而且攻击者可以换着 id 刷，挡不住。

解法二：布隆过滤器。 在 Redis 前面加一道「可能存在」的快速判断，把不存在的 key 直接拦在缓存之外。这是本文的重点。

2.3 布隆过滤器的原理

布隆过滤器（Bloom Filter）是一个「说没有就一定没有，说有不一定有」的概率数据结构。它由两部分组成：

  • 一个长度为 m 的位数组，初始全 0；
  • k 个哈希函数，每个都能把元素映射到位数组的某个下标。

写入：元素进来，用 k 个哈希函数算出 k 个下标，把这 k 个位置全部置 1。

查询：同样算出这 k 个下标，检查：

  • 只要有一个位置是 0 → 元素一定不存在（因为存在的话这 k 位早被置 1 了）；
  • 全部都是 1 → 元素可能存在（可能是真存在，也可能是别的元素把这几位占了，叫误判）。

关键性质：

  1. 不会漏报（False Negative 为 0）——存在的一定会被判为可能存在；
  2. 可能误报（False Positive 非 0）——不存在的可能被误判为可能存在；
  3. 只增不删——位数组一旦置 1 就回不去，删除单个元素很难（需要计数布隆）。

为什么会有误判？因为位数组长度有限，多个元素共享同一个位。比如「商品 A」和「商品 B」都命中了第 5 位，那查一个从没写入过的「商品 C」时，如果它的 k 个下标恰好都被 A、B 覆盖了，就会被误判为「可能存在」。

误判率可以由位数组大小 m、哈希函数个数 k、元素个数 n 三者控制：

m 越大、n 越少，误判率越低。工程上通常把误判率控制在 1% 甚至 0.1%。

布隆过滤器的边界：它只能告诉你「可能不存在」，一旦误判，请求还是会打到 DB（只是概率很低）。而且数据有增删时，过滤器需要同步维护，删除尤其麻烦。所以它适合「读多、key 集合相对稳定」的场景。

三、缓存击穿与 singleflight

穿透挡的是「不存在的请求」，击穿挡的是「存在的请求太多」——这是两个方向的问题，解法也完全不同。

3.1 击穿是怎么发生的

根因在于：缓存回填有延迟（一次 DB 查询的耗时），在这段窗口里，后来者仍然看不到缓存。 所以「先查缓存、没有再查库、再回填」这套标准 Cache-Aside 流程，在并发下是有洞的——它默认了「我查库的时候别人不会查」。

要补这个洞，思路只有一条：让同一个 key 的并发请求合并，只放一个去查库。 Go 里现成的工具就是 golang.org/x/sync/singleflight。

singleflight 的核心结构非常短，就一个 map + 一把锁 + 每个 key 一个 WaitGroup：

注意 call 的字段被分成了两组，用两种不同的机制保护：

字段 保护机制 原因
val、err WaitGroup 的 happens-before，不用锁 Done 之前只写一次，之后只读
dups、chans Group.mu 互斥锁 多个 follower 会并发 dups++

这是理解 singleflight 的钥匙：锁保护的是「登记」，WaitGroup 保护的是「结果传递」。

这段代码里藏着三个顺序不能颠倒的细节：

  1. g.m[key] = c 必须在 Unlock 之前。 顺序反了会有一个窗口，让第二个 goroutine 也查不到 key，于是出现两个 leader、重复查库——整个库就白用了。
  2. g.mu.Unlock() 必须在 c.wg.Wait() 之前。 锁在 Wait 前不放，leader 在 doCall 收尾时 g.mu.Lock() 就永远拿不到锁，直接死锁。
  3. c.dups++ 必须在锁内。 多个 follower 会并发改这个字段，放锁外就是 data race（实测 100 万次自增会丢 26.78%）。

两个要点：

  • 先写 val、再 Done。 顺序反了 follower 被唤醒时读到的是零值。
  • if g.m[key] == c 这个判断不能省。 有人中途调 Forget(key) 后，新的 goroutine 会往 map 里塞一个新的 call，此时无脑 delete 会误删新 call。

而 delete(g.m, key) 这一行揭示了 singleflight 的本质：它不做缓存，结果只在「飞行期间」共享。 fn 一返回，key 就从飞行表摘掉，下一次 Do 是全新的一次执行。它是去重，不是记忆。

3.4 三个必须知道的坑

  • Do 没有 context，进去就同步阻塞，超时控制不了。 要超时，用 DoChan + select：
  • 超时后不 Forget，下一个请求还会撞上那个没跑完的慢调用。 上游超时 100ms、下游要 300ms，在 leader 跑完之前，这个 key 的所有请求都在陪葬。

3.5 一个重要边界

singleflight 只在单个进程内有效。Group 就是进程内的一块 map，跨 Pod 完全不共享。你部署 5 个实例，热点 key 过期照样 5 次查库。要跨实例去重，得上 Redis 分布式锁（SETNX）或「逻辑过期」方案——这是它最容易被忽视的边界。

四、缓存雪崩：几个解决方法（简述）

雪崩是「一大批 key 同时过期」或「Redis 整个挂掉」导致的流量集中打库。常用的几个解法：

  • 过期时间加随机抖动：给 TTL 加一个随机偏移，避免集中过期。
  • 热点数据永不过期 + 逻辑过期：物理 TTL 设很大，在 value 里存一个「逻辑过期时间」，后台异步刷新。
  • 多级缓存：本地缓存（如 bigcache/freecache）+ Redis，Redis 挂了本地还能扛一层。
  • 限流与降级：Redis 不可用时，接口降级返回默认值或直接熔断，保护 DB。
  • 集群高可用：Redis 主从 + 哨兵 / Cluster，避免单点整个挂掉。

雪崩和击穿本质不同：击穿是「一个 key」的并发合并问题，雪崩是「一批 key + 一个中间件」的可用性问题，所以解法也不在一个维度上。

五、总结

问题 本质 核心解法 Go 里的工具
穿透 查不存在的 key 布隆过滤器 / 空值缓存 bits-and-blooms/bloom
击穿 热点 key 并发重复查 合并同一 key 的请求 x/sync/singleflight
雪崩 key 集中过期 / Redis 挂 TTL 抖动 / 多级缓存 / 降级 工程手段

最后把 singleflight 再浓缩成一句话：

一个 map[string]*call + 一把锁 + 每个 key 一个 WaitGroup。先到的当 leader 查库，后到的 Wait 等结果；leader 算完 Done 唤醒所有人，然后从表里删掉。它不缓存结果，只合并「正在进行中的同一份计算」。
