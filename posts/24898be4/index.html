gRPC 的学习以及简单实现总结

本文是我从零系统学习 gRPC（Go 语言）的总结：先按学习路线梳理每个知识点的核心和实现要点，再记录学习过程中遇到的概念疑问。完整可运行代码见 GitHub 仓库（替换成你的实际仓库地址），每个知识点对应一个独立目录。

一、学习路线

小节 主题 代码目录
1 Hello World（一元 RPC） 01-hello/
2 Protobuf 语法 02-protobuf/
3 四种服务类型（流式） 03-streaming/
4 错误处理 04-error/
5 超时 Deadline 05-deadline/
6 Metadata 06-metadata/
7 拦截器 07-interceptor/
8 TLS + 反射 + 健康检查 08-tls/

说明：环境搭建（安装 protoc 和插件）没有代码目录；反射和健康检查因为都是”几行代码就能用”，直接加在了 08-tls/ 的服务端里。

二、各知识点核心与实现要点

1. Hello World：一元 RPC（01-hello/）

整个 gRPC 的核心链路就四步：

  • 服务端四步：net.Listen 监听端口 → grpc.NewServer() 建服务 → RegisterXxxServer(s, &impl{}) 注册实现 → s.Serve(lis) 启动。
  • 客户端四步：grpc.NewClient(addr, ...) 建连接 → NewXxxClient(conn) 拿桩 → context.WithTimeout 设超时 → client.SayHello(ctx, req) 直接调用。
  • 生成代码后，服务端只需要实现 SayHello 方法体，客户端像调本地函数一样调它，网络、序列化、HTTP/2 全被框架包了。

2. Protobuf 语法（02-protobuf/）

.proto 是服务端和客户端之间的”合同”。核心语法及它映射到 Go 的类型：

proto 写法 生成的 Go
string name = 1; Name string
repeated string tags = 9; Tags []string
map<string,string> attrs = 12; Attrs map[string]string
optional string nick = 14; Nick *string（指针，nil 表示”没填”）
enum Gender type Gender int32 + 一串常量
oneof contact 接口 + 包装类型

几个关键点：

  • = 1 不是赋值，是字段编号（序列化时用它代替字段名），一旦使用别改。
  • **optional 解决”区分没填和填了默认值”**：不加它，name="" 分不清是”没填”还是”名字就是空”。
  • oneof 表示多选一，设置新字段会自动清掉旧字段。
  • 枚举第一个值必须是 0（默认值）。

3. 四种服务类型（03-streaming/）

这是 gRPC 相对普通 HTTP 接口最大的优势。区分它们的唯一依据是 stream 关键字的位置：

规则一句话：stream 写在哪个消息前，哪边就是流。

流式全靠这几个方法，务必分清：

方法 谁能用 作用
stream.Send(m) 双方 发一条
stream.Recv() 双方 收一条，返回 io.EOF 表示对端发完
stream.SendAndClose(m) 服务端 发最后一条并关闭（客户端流式）
stream.CloseAndRecv() 客户端 关闭发送端 + 收汇总（客户端流式）
stream.CloseSend() 客户端 关闭发送端（双向流）

最容易踩的坑：io.EOF 不是错误，是”流正常结束”的信号。处理时要先判 err == io.EOF，再判其他错误。

4. 错误处理（04-error/）

gRPC 不用普通 Go error 表达业务错误，而是用状态码（status code），类似 HTTP 的 200/404/500。

  • 服务端抛：return nil, status.Errorf(codes.NotFound, "找不到用户 %s", name)（第一个返回值是 nil，第二个是 error）。
  • 客户端接：st, ok := status.FromError(err)，然后 st.Code() 拿状态码、st.Message() 拿消息。

常用状态码：InvalidArgument（参数非法）、NotFound（不存在）、AlreadyExists（已存在）、PermissionDenied（没权限）、Unauthenticated（未认证）、DeadlineExceeded（超时）、Unavailable（服务不可用）、Internal（内部错误）。

5. 超时 Deadline（05-deadline/）

  • 客户端设超时：ctx, cancel := context.WithTimeout(context.Background(), 3*time.Second)。
  • 自动传播：deadline 会随请求自动传给服务端，不用手动传；而且传的是”绝对截止时间”，多跳转发也准确。
  • 服务端感知：用 select 同时监听任务完成和客户端取消：

即使服务端不检查 ctx.Done()，客户端到点也会收到 DeadlineExceeded；服务端检查它是为了及时止损——客户端都跑了，就别再傻算 3 秒了。

6. Metadata（06-metadata/）

Metadata 相当于 HTTP 的 header，是双向的：

  • 客户端 → 服务端：metadata.AppendToOutgoingContext(ctx, "authorization", "Bearer xxx") 发，服务端 metadata.FromIncomingContext(ctx) 读。主要用来传 token、trace-id。
  • 服务端 → 客户端：grpc.SetHeader(ctx, md) / grpc.SetTrailer(ctx, md) 发，客户端 grpc.Header(&md) / grpc.Trailer(&md) 收。

header 和 trailer 的区别：header 在响应消息前发，trailer 在后发（所以”耗时”这种最后才知道的信息放 trailer）。

7. 拦截器 Interceptor（07-interceptor/）

拦截器就是 gRPC 的”中间件”，在 RPC 调用前后插入统一逻辑（鉴权、日志、计时、panic 恢复）。

  • 服务端：grpc.NewServer(grpc.UnaryInterceptor(fn))，签名 func(ctx, req, info, handler) (resp, err)。
  • 客户端：grpc.NewClient(..., grpc.WithUnaryInterceptor(fn))，签名 func(ctx, method, req, reply, cc, invoker, opts...) error。

核心是理解 handler（服务端）和 invoker（客户端）——它们是”包装了真正逻辑”的函数：调 handler(ctx, req) 才执行你的业务函数，调 invoker(...) 才真正发起网络请求。拦截器之所以能”拦截”，就在于不调它，业务逻辑就不执行（鉴权失败直接 return，请求被挡在门外）。

8. TLS + 反射 + 健康检查（08-tls/）

  • TLS：服务端 grpc.NewServer(grpc.Creds(creds))，客户端 grpc.NewClient(..., grpc.WithTransportCredentials(creds))，替代之前的明文 insecure。单向 TLS 验证的是”服务端是真的”；要验证客户端身份需要 mTLS。
  • 反射：reflection.Register(s) 一行开启，让 grpcurl 等工具能发现和调用服务。
  • 健康检查：health.NewServer() + SetServingStatus("", SERVING) + RegisterHealthServer，供 K8s / 负载均衡探活。

三、学习过程中遇到的问题

学习过程中问过不少”这是什么、它是干什么的”，把有代表性的整理在这里。

Q1：一个 gRPC 项目里为什么有那么多”名字”？

最开始被包名绕晕过，其实一个项目里同时存在几套名字：

名字 写在哪 是什么
grpc-study go.mod Go 模块名（导入路径的根）
hello proto package hello; proto 命名空间，跟 Go 包名无关
grpc-study/01-hello/pb;pb proto go_package 分号前是导入路径，分号后是 Go 包名
pb 生成文件 package pb Go 包名（写代码时的称呼）
grpc-study/01-hello/pb 代码 import 导入路径（去哪找）

三条规则想通就清晰了：① proto 的 package 和 Go 包名是两回事；② 导入路径 ≠ 包名（路径是”地址”，包名是”称呼”）；③ import pb "..." 里的 pb 是别名，不写时 Go 自动用包的声明名。

Q2：为什么 client 和 server 的 package 都是 main？

因为 Go 里只有两种包：package main 是可执行程序（必须有 func main() 入口），其他包是库（只能被 import）。

server 和 client 是两个独立运行的程序，要分别在两个终端启动，各自都需要自己的入口 func main()，所以都是 package main。而生成的 pb 包是库，没有 main，只能被 import、不能 go run。

目录名叫 server/client 无所谓，真正决定”是不是可执行程序”的是文件里的 package main。

Q3：拦截器有什么用？handler 和 invoker 到底是什么？

拦截器 = 中间件，作用是把鉴权、日志、计时这些”每个方法都要做的横切逻辑”集中到一处，业务代码保持干净。只有一两个方法时看不出价值，几十个方法时就是刚需。

handler（服务端）和 invoker（客户端）是理解拦截器的关键——它们是”包装了真正逻辑的函数“：

所以调 handler(ctx, req) = 间接调你的 SayHello；调 invoker(...) = 真正发起网络请求。拦截器之所以能”拦截”，就在于不调它们，业务逻辑就不执行。

Q4：拦截器注入 token 和手动加 metadata 有什么区别？

两者是”隐式 vs 显式、集中 vs 分散”的关系：

  • 手动加（06-metadata/）：每次调用都写 AppendToOutgoingContext，容易忘、到处重复。
  • 拦截器注入（07-interceptor/）：在拦截器里统一加，之后所有调用自动带上，业务代码里完全不用管 token。

好处是横切逻辑集中一处，写 100 个调用只要挂一次拦截器，100 个都自动生效，也不会漏。

Q5：写流式方法为什么报错？（新版泛型 API）

遇到过一个很新的问题：较新的 protoc-gen-go-grpc（v1.6.x）生成的流式接口已经改成泛型写法，和网上老教程不同：

老类型名被保留成了别名，所以老代码还能跑。最稳的做法：写实现前打开生成的 *_grpc.pb.go，搜 XXXServer interface，照着签名抄——这永远是正确答案。

四、总结

这次学习走完了从环境搭建到 TLS 的完整链路。最有价值的收获，不是背下 API，而是：

  1. 理解 gRPC 的本质：proto 契约 + 代码生成 + 框架包办网络，你只写业务。
  2. 掌握流式的 stream 规则和 Send/Recv 家族——这是 gRPC 相对 HTTP 的核心优势。
  3. 搞清”名字”关系——proto 包名、go_package、Go 包名、导入路径、别名，这套概念想通之后，看任何 gRPC 代码都不再晕。
  4. 会用拦截器做横切逻辑——鉴权、日志、计时统一收口。

完整代码、每节的实现细节和运行方式，见仓库各目录下的源码与注释。
